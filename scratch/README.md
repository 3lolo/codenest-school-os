# Self-hosted Scratch 3.0 editor

This folder is a **prebuilt, static copy of the real, official Scratch 3.0
editor** — [scratchfoundation/scratch-gui](https://github.com/scratchfoundation/scratch-gui),
the same open-source project that powers scratch.mit.edu — built from
source and committed here as plain static files (`index.html` + `gui.js` +
`static/` + `chunks/`). It is **not** generated by this project's own
`build.mjs`/webpack setup; `build.mjs` just copies this folder straight
into `dist/scratch/` on every build (see the `cp(... "scratch" ...)` line).

It's served at `/scratch/` and embedded via an iframe from the app's
"Scratch" nav tab (`scratchView()` in `src/app.js`) — same-origin, so no
`X-Frame-Options` issue, and it needs no backend of its own: everything
(sprites, blocks, running a project) happens entirely in the student's
browser. Saving/loading a project uses the editor's own "File" menu
(save/load a `.sb3` to the student's computer) — there's no server-side
project storage, same as the plain desktop/offline Scratch app.

## Known limitations of this build

- **No physical micro:bit firmware flashing.** The micro:bit extension's
  block palette works, but the one-time "flash this onto a real micro:bit
  over USB" step is a no-op — building this required downloading Scratch's
  micro:bit `.hex` firmware from `downloads.scratch.mit.edu`, which wasn't
  reachable from the environment this was built in. Irrelevant unless the
  school has physical micro:bit boards.
- **No camera/microphone.** The site's `vercel.json` sends a site-wide
  `Permissions-Policy: camera=(), microphone=()` header, so the "Video
  Sensing" extension (and anything else wanting the camera/mic) won't get
  permission. That header is deliberate elsewhere in the app; loosen it
  only for `/scratch/*` if a class specifically needs Video Sensing.
- Only the full editor entry (`gui`) was built — the alternate
  `blocks-only` / `compatibility-testing` / `player` embed pages scratch-gui
  also ships (meant for other embedding scenarios) were dropped to keep
  the build both smaller and buildable at all in a memory-constrained
  environment (see below). Nothing in the app links to those, so this
  doesn't remove anything a user could reach.

## How this was built (and how to rebuild/update it later)

```bash
git clone https://github.com/scratchfoundation/scratch-gui.git
cd scratch-gui
```

Two upstream things needed working around to get a build at all:

1. **`npm install` runs a `prepublish` script that downloads Scratch's
   micro:bit firmware** from `downloads.scratch.mit.edu`. If that host
   isn't reachable from your build machine, `scripts/prepublish.mjs`'s
   `downloadMicrobitHex()` needs a try/catch fallback that writes a
   placeholder `.hex` file instead of throwing — otherwise `npm install`
   fails outright before it even gets to building anything.

2. **The production build easily gets OOM-killed** on a memory-constrained
   host (this was built under a ~5.8GB limit, 2 CPUs). Two changes fixed
   it, both inside `node_modules/scratch-webpack-configuration/src/index.cjs`
   (the shared config builder scratch-gui's own `webpack.config.js` uses):
   - `devtool: 'cheap-module-source-map'` → `devtool: false` (skip source
     maps — they roughly double Terser's peak memory for a bundle this
     size, and we don't need them for a static self-hosted build anyway).
   - `TerserPlugin({ parallel: 2 })` → `{ parallel: 1 }` (their own comment
     says `parallel: 2` already halves peak memory vs. the default on a
     big machine — 2 was still enough to OOM-kill here, 1 wasn't).

   Also, `webpack.config.js`'s own `entry` object was trimmed from four
   entries (`gui`, `blocksonly`, `compatibilitytesting`, `player`) down to
   just `gui` (and the three now-unused `HtmlWebpackPlugin` blocks for the
   others removed) — building all four at once was the other big memory
   cost, and we only ever serve `gui`.

   If rebuilding on a machine with more memory (roughly 8GB+ should be
   comfortable), none of this should be necessary — the plain upstream
   `npm run build` ought to just work.

3. Then, critically, **build with plain `npm run build` (`NODE_ENV` left
   unset)**, not `NODE_ENV=production`. Confusingly, `webpack.config.js`
   uses `NODE_ENV=production` for a *different* purpose — it picks between
   two totally different build targets (`dist/scratch-gui.js`, an
   embeddable *library* build for npm consumers, vs. `build/`, the actual
   standalone editor app we want) — while the *minification* setting is
   controlled separately inside `scratch-webpack-configuration`. If you
   patch that package to always minify (as this build's copy does — see
   `isProduction = true` hardcoded in step 2's file), you get a minified
   `build/` output *without* setting `NODE_ENV=production`, which is what
   you want. Setting `NODE_ENV=production` (the "obvious" thing to try)
   silently builds the wrong target instead.

Then copy `build/*` here (drop the `.map`/`.LICENSE.txt` files — not
needed for serving), replacing this folder's contents, and run this
project's own `node build.mjs` / test suite as usual.
